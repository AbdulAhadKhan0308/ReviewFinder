RESTAURANT REVIEW PLATFORM — REQUIREMENTS

This is a product requirements document, not a Python dependency file.
It holds the requirements from the supplied brief, plus the implementation
decisions and answers to questions agreed while building the platform; together
they are the committed scope. Acceptance criteria are in acceptance.txt.

1. PURPOSE

Build a simplified restaurant review platform with two account roles:
- Reviewer: discovers restaurants, reads restaurant details and reviews, and writes reviews.
- Restaurant owner: manages restaurants that belong to their account.

2. CONFIRMED FUNCTIONAL REQUIREMENTS

Accounts and authentication
- Users can register with an email address and password.
- Users choose reviewer or restaurant owner during registration.
- Registered users can sign in with their email and password.

Reviewer experience
- Authenticated reviewers can list all restaurants.
- Each listing shows the restaurant name and relevant summary information.
- Selecting a restaurant opens its detailed view, preferably a separate route.
- Users can filter restaurants by cuisine and average rating.
- Default sorting is average rating from highest to lowest.
- Users can switch sorting to lowest to highest.
- Selected filters and sorting persist when users leave and revisit the app.

Owner experience
- Authenticated owners can list their own restaurants.
- Owners can create, view, update, and delete their restaurants.
- Owners cannot update or delete restaurants owned by another account.

Restaurant information
- Title/name.
- Preview image.
- Location.
- Description.
- Reviews.
- Cuisine is also necessary to support the required cuisine filter.

3. CONFIRMED TECHNICAL AND QUALITY REQUIREMENTS

- A web implementation must be a single-page application; a hydrated hybrid
  framework is acceptable. Fully server-rendered fragment frameworks such as
  Turbolinks/Hotwire are not acceptable.
- Handle unexpected scenarios and edge cases.
- Enforce secure authentication and authorization.
- Validate input and display understandable validation errors.
- An optional Material UI boilerplate may be used, modified, or ignored.

4. AGREED IMPLEMENTATION DECISIONS

- Build a responsive website for desktop and mobile browsers.
- Use one role per account and keep it fixed after registration for the MVP.
- Include sign-out and session expiration handling.
- Enforce roles and ownership on the server for every protected operation.
  Derive the owner identity from the authenticated session, not submitted data.
- Store passwords using an established password-hashing implementation.
- Use secure session handling and protect authentication endpoints against abuse.
  Sessions use an httpOnly cookie that expires after 7 days without use; accounts
  lock for 5 minutes after 5 failed sign-ins.
- Validate data on the server as well as in the browser.
- Max lengths: title 100, location 200, description 2,000, review text 2,000,
  email 254, display name 50 characters. Title, location, description and display
  name are required. Trim input and reject blank-only values.
- Passwords: 8 to 128 characters, with no forced symbols or digits.
- Treat email addresses case-insensitively for account uniqueness. Later, one email
  may hold one reviewer account and one restaurant owner account (see Q12).
- Persist restaurant, user, and review data in a database.
- Persist browsing preferences per account in the same browser initially.
- Use a controlled cuisine list, stored in the database, to avoid inconsistent filter
  values. Start with Italian, French, Chinese, Japanese, Indian, Mexican and Greek.
  Each restaurant has 1 to 3 cuisines.
- Show unrated restaurants as 'No reviews' and place them last in either sort.
- Use a stable secondary sort when ratings are equal: title, then ID.
- Restaurant cards show image, name, cuisines, location, average rating (or
  'No reviews') and review count.
- The detail page lists reviews newest first by default, each with author name,
  rating, text and date.
- Display loading, empty, no-results, validation, and request-failure states.
- If cookies are blocked, show a message asking the user to enable them for this
  site, since sign-in needs cookies.
- Require confirmation before restaurant deletion.

6. QUESTIONS AND ANSWERS

Priority A: core behavior

Q1. Are we building a responsive web app only, or is a native mobile app needed?
Answer: Responsive web app only.

Q2. Is there a required or preferred frontend/backend stack and database?
Is the mentioned Material UI boilerplate available, or should we start fresh?
Answer: For frontend let's do React + Material UI (for styles), for backend let's do C#/.NET/PostgreSQL.
Use Tailwind only as a reference point.

Q3. Can reviewers create reviews, or are reviews only displayed from seed data?
If they can write reviews, can they edit/delete their own reviews, and is there
one review per reviewer per restaurant or multiple reviews?
Answer: A reviewer can write, edit and delete their own reviews, and can post more than one review for the same restaurant.
Reviews are published as soon as they are written; there is no approval or moderation step.
Known limitation: one reviewer can post many reviews and skew a restaurant's average.

Q4. What is the rating scale, and is review text mandatory?
Answer: Integer ratings from 1 to 5, text is optional

Q5. Does rating filtering mean a minimum threshold, an exact rating, or a range?
Should filtering use the actual average or its displayed rounded value?
Answer: minimum threshold and range should be supported. The average rating is rounded to 2 decimals;
that rounded value is shown in the UI and is also used for filtering and sorting.
Min and max can be decimals from 1 to 5 (up to 2 places); both limits are inclusive.
Restaurants with no reviews are hidden when a rating filter is active.

Q6. Can a restaurant have multiple cuisines? Can users select multiple cuisines
in the filter, and should matching any selected cuisine be sufficient?
Answer: Yes, restaurants can have multiple cuisines, and users can select multiple cuisines.
When multiple cuisines are selected, only restaurants that have all the selected cuisines are shown.

Q7. Must users sign in to browse restaurants? Can owners also browse all
restaurants, and are owners permitted to write reviews?
Answer: Sign-in is required to browse. Owners manage only their own listings: they can't browse anyone else's restaurants and can't write reviews, including on their own restaurants.
Reviewers can browse and write reviews on restaurants.

Q8. How should preview images be provided: URL, file upload, or both?
Answer: File upload only. If no image is uploaded, the app shows a default image.
Allowed formats: JPG/JPEG, PNG, WebP; maximum size 5 MB.
Owners add, change or remove the image on both the create and edit forms; it's
saved together with the rest of the form.

Q9. What does location contain: free-text address, city, or structured address?
Are maps or geolocation required?
Answer: Plain-text address is fine; no maps or geolocation.

Priority B: scope and edge-case behavior

Q10. Should filters/sorting follow an account across devices, or only persist
in the same browser? Should preferences be separate for different accounts?
Answer: Same browser, separate preferences per account.

Q11. Are email verification and password reset required for this submission?
Answer: Will include email verification and password reset (lower priority; work on it later).
Users can't sign in until their email is verified.
Status: Neither is built yet; the current sign-in sends no emails. Password reset
must be built afterwards. Until email verification is built, users can sign in
without verifying their email.

Q12. Can users change roles or have both roles under one email address?
Answer: One fixed role per account. Later, the same email address can be used to
register twice: once as a reviewer and once as a restaurant owner, as two separate
accounts. Not built yet: for now each email can register only once.
When built, sign-in will need to know which of the two accounts the user means.

Q13. When an owner deletes a restaurant, should its reviews also be deleted?
Is recovery/soft deletion required? May owners remove individual reviews?
Answer: Deleting a restaurant also deletes its reviews, with no recovery. Owners
can't edit or delete individual reviews.

Q14. Where do unrated restaurants go in the sort, and how are equal ratings ordered?
Answer: Unrated restaurants come last in both sort orders; equal ratings are
ordered by title, then ID.

Q15. Is pagination required? Are search by name, admin tools, moderation,
owner replies, or review photos expected?
Answer: All lists are paginated. Keyword search is included for the reviewers'
restaurant list (title, location and description) and for reviews (review text).
Reviews can also be filtered by rating range and date range, and sorted by rating
or date (see data-model-and-api.txt section 4). Owners' own-restaurant list has no
filters or sorting. Admin tools, moderation, owner replies and review photos are
out of scope.

Q16. Are there branding/design references, a deadline, or submission rules?
Should delivery include hosting, source code, setup instructions, demo accounts,
seed data, automated tests, or a recorded demo?
Answer: Not answered yet.

8. BUILD PROGRESS

Work is built in pieces, each covering server and client together.

[x] 0. Accounts: register, sign in, sign out; session cookie, CSRF protection,
       account lockout. Every API endpoint requires sign-in unless marked public.
[x] 1. Owner restaurant management: owners create, view, edit and delete their own
       restaurants; 1 to 3 cuisines each; delete asks for confirmation.
[x] 2. Image upload: add, replace and remove a restaurant image (JPG/JPEG, PNG,
       WebP, up to 5 MB) on the create and edit forms, saved with the form;
       default image when none is uploaded.
[x] 3. Reviewer restaurant list: restaurant cards, pagination, keyword, cuisine and
       rating filters, sorting by rating, filters and sort remembered in the
       browser.
[x] 4. Reviews: reviewers write, edit and delete their own reviews; reviews listed
       on the restaurant page with keyword, rating and date filters, sorting by
       rating or date, and pagination; average rating and review count update.
[ ] 5. Edge cases and polish: empty, error and not-found states; access checks via
       direct API calls; mobile layout.
[ ] 6. Delivery: README with setup steps, demo accounts and sample data, plus
       whatever Q16 asks for.

Postponed, not part of this submission: password reset, email verification (Q11),
and registering one email once per role (Q12).
